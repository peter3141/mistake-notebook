## 3. RLS 策略（全表，用户只能增删改查自己的数据）

- PART I 的 16 张表与 PART II 的 13 张新表**全部**执行：

```sql
alter table public.<表> enable row level security;
create policy "own_rows" on public.<表>
  for all to authenticated
  using (auth.uid() = user_id)
  with check (auth.uid() = user_id);
```

- 唯一例外仍是 `profiles`（主键列名是 `id`），PART I 已做列名分支。
- 未登录 `anon` 对上述表**没有任何策略** = 完全不可访问。
- 只读分享页是唯一使用 `service_role` 的地方，且经过 token / 过期 / 撤销三重校验，只 SELECT 白名单字段。
- Storage 私有桶 `mistake-images` 四条策略不变，路径第一段必须是自己的 `auth.uid()`；笔记等通用附件沿用同一桶与同一前缀规则。

## 4. 统一回收站怎么工作

1. 业务表统一带 `deleted_at`；前端删除时只执行 `update ... set deleted_at = now()`。
2. 六张主表（`mistakes` / `schedules` / `tasks` / `notes` / `habits` / `goals`）各有一个 `after insert or update of deleted_at` 触发器，调用 `public.sync_trash_item(类型, 标题列)`，自动往 `trash_items` 登记或注销。
3. 前端 `/trash` 只需一次 RPC：

```sql
select public.unified_trash();
-- 返回 [{ id, entity_type, entity_id, title, deleted_at, expires_at }, ...]
```

4. 恢复 / 彻底删除：

```sql
select public.restore_trash_item('note', '这里填 entity_id');
select public.purge_trash_item('schedule', '这里填 entity_id');
```

5. 清空（30 天到期）：

```sql
select public.purge_expired_trash();  -- 返回被清理的条数
```

> **安全**：三个函数都是 `security definer`，内部先用 `case ... when` **白名单映射表名**（杜绝 SQL 注入），再叠加 `user_id = auth.uid()` 过滤，越权操作会静默影响 0 行。
> **前端必须做二次确认**：清空回收站、注销账号、彻底删除都弹确认框（注销/清空还需输入指定文字），沿用前 6 段规则。
