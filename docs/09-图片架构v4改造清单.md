# 第 1 步 · 图片存储架构 v4 改造清单与迁移说明

> 适用范围：对已完成 v2 + v3 的「个人综合管理网站」做**增量改造**，只动图片链路与整题上传流程。
> 对应 SQL：`supabase/schema.sql` **PART IV**（追加在文件末尾，整份从头执行一次即可，幂等、可重复执行、不丢数据）。
> 本文不含任何真实密钥。

---

## 一、先说核查结论（很重要，避免误判）

我逐行检查了现有 `supabase/schema.sql` 与全部前后端代码，结论是：

| 检查项 | 现状 | 是否需要改 |
| --- | --- | --- |
| `mistake_images` / `attachments` / `ocr_jobs` 有无 Base64、Blob、`bytea` 字段 | **没有**。只有 `storage_path text`、`mime_type`、`width/height`、`size_bytes` | 不需要清理现有数据；但补了幂等 `drop column` 兼容更早的库 |
| 桶是否私有 | `mistake-images` 已 `public = false`，4 条 `storage.objects` 策略按 `foldername(name)[1] = auth.uid()` 隔离 | 加固：单文件上限 8MB、文件名正则、显式 MIME 白名单 |
| 取图方式 | 列表/详情/打印/分享/Word/Anki 已用 `createSignedUrls` 或服务端下载 Storage 文件 | 保持；修掉分享页签名时长与链接过期时间不一致的问题 |
| 富文本图片 | 笔记用 `data-storage-path`；**但 Tiptap 开了 `allowBase64: true`、`sanitizeHtml` 允许 `data:image/`**，粘贴图片会写进 HTML | **必须改**：禁止新 Base64，历史 Base64 展示时提示迁移 |
| 删除单张图片 | `deleteMistakeImage()` **立即物理删除 Storage 文件** | **必须改**：先进图片回收站，彻底删除才删文件 |
| 整题原图标记 | 无 | **新增** `image_role` 等字段 |
| OCR 与原图关系 | `ocr_jobs.image_path` 只是文本，无强关联 | **新增** `image_id` 外键 + 独立结果字段 |
| 孤儿文件清理 | 无 | **新增** 只读清单函数 + 用户确认后删除 |
| 导出原图包 | 无（只有 JSON/CSV/Word/Anki） | **新增** zip 导出 |

**所以本次不是「把 Base64 搬到 Storage」的大迁移，而是补齐角色标记、图片回收站、OCR 独立记录、整题上传链路，并堵住新 Base64 的入口。** 现有图片数据一行都不用动。

## 二、改了哪些表、哪些字段、为什么

### 2.1 `mistake_images`（错题图片主表）

| 字段 | 类型 | 为什么加 |
| --- | --- | --- |
| `image_role` | `text`，枚举 `original / cropped / inline / thumbnail`，默认 `inline` | 区分「整题原图」「手动裁剪图」「富文本内嵌图」「缩略图」。整题图不能被当成普通插图处理 |
| `parent_image_id` | `uuid` → 本表 id | 裁剪图记录来自哪张整图；删除整图时据此提示「有 N 张裁剪图关联」 |
| `crop_rect` | `jsonb` | 可选记录裁剪区域坐标 `{x,y,w,h}`，便于重裁/核对 |
| `original_size_bytes` / `compressed_size_bytes` | `int` | 记录压缩前后体积，用于进度提示、容量说明、验证「压缩后再上传」 |
| `thumbnail_path` | `text` | 前端 canvas 生成的缩略图路径（**不依赖 Supabase 图片变换**，免费额度也能用） |
| `public_url` | `text`，可空 | 仅当用户主动把桶设为公开时填完整 URL；**私有桶保持 NULL**，展示时现签，避免把会过期的签名 URL 存进库变成脏数据 |
| `is_original_backed_up` / `original_backup_note` | `boolean` / `text` | 区分「展示图」与「用户是否已手动做本地原图备份」。**网页功能完全不读这两个字段** |
| `ocr_job_id` | `uuid` → `ocr_jobs` | 整图关联的 OCR 任务，便于查看/重试/缓存 |
| `is_ai_description` | `boolean` | 标记 AI 图形描述，打印默认排除 |
| `draft_id` | `uuid`，可空 | 新建错题页要先上传整题图，此时还没有 `mistake_id`；保存错题时再绑定 |
| `created_by` | `text` | 区分用户上传 / 迁移脚本写入 |
| **`mistake_id` 由 NOT NULL 改为可空** | — | 配合 `draft_id`，约束 `chk_mistake_images_bound` 保证二者至少有一个，不会出现「无主图片」 |

> 保留不动：`id`、`user_id`、`storage_path`（唯一图片数据来源）、`mime_type`、`width/height`、`size_bytes`、`sort_order`、`created_at`。

### 2.2 `attachments`（笔记等通用附件）

补齐 `image_role`、`parent_image_id`、`crop_rect`、`width/height`、`original_size_bytes` / `compressed_size_bytes`、`public_url`、`is_original_backed_up`、`original_backup_note`。
理由：与 `mistake_images` 同一套元数据口径，孤儿文件扫描与导出原图包可以统一处理。**依然只存 `storage_path`，不存任何图片数据。**

### 2.3 `ocr_jobs`（OCR 任务）

| 字段 | 为什么 |
| --- | --- |
| `image_id` → `mistake_images(id)` | **OCR 结果和原图是两条独立记录**：文字写入题干后原图仍在；删改题干不影响原图 |
| `options` / `formulas` | 结构化 OCR 输出：选项文字、公式文本 |
| `figure_description` / `is_ai_description` | AI 图形描述，必须标注「AI 描述，仅供参考」，**打印默认不打印** |
| `confidence` | 置信度提示（模型给了才填，没有就留空，不编造） |
| `source` | `ai` / `local`，区分 Coding Plan OCR 与浏览器本地 OCR |
| `applied_at` / `applied_field` | 只有用户点「确认应用」后才写，用于审计和防止重复写入 |

原有 `raw_text`、`result_json`、`status`、`model`、`error` 全部保留。

### 2.4 新增 `deleted_images`（★ 图片级回收站）

删除一张图片时：把这条记录**连同 `storage_path` 复制进 `deleted_images`**，再删主表行，**Storage 文件保持不动**。
彻底删除 / 清空回收站时：客户端才调用 `storage.remove()`，成功后写 `purged_at`。
这解决了两个问题：

1. 主表查询**完全不用加 `deleted_at` 过滤**，所有既有联表 SQL、RLS、导出代码都不用改，不破坏现有功能；
2. 「删除错题进回收站，Storage 文件保留；彻底删除后才删」有可查的数据库记录，30 天内可恢复。

字段：`user_id`、`source_table`、`source_id`、`mistake_id`、`storage_path`、`image_role`、`parent_image_id`、`meta`（原始元数据快照）、`deleted_at`、`expires_at`（30 天）、`purged_at`。

### 2.5 新增 `image_purge_failures`

`storage.remove()` 失败时登记，避免「数据库删了、Storage 还留着却没有任何记录」。设置页可查看并重试。

### 2.6 新增视图 `full_page_captures`

把 `image_role='original'` 的整图与其最近一次 OCR 结果、裁剪图数量并排列出，供详情页「整题原图 + OCR 文字对照」和「删除前检查裁剪图引用」使用。

### 2.7 新增函数 `list_orphan_images_v4(limit)`

只读列出「Storage 里有、数据库没引用」的文件。排除：

- `mistake_images` / `attachments` 中登记的路径
- `deleted_images` 中未彻底删除的路径（**不能误删回收站里的图**）
- `mistakes.content/answer/analysis` 与 `notes.content` 中以 `data-storage-path` 引用的路径（**不能误删富文本仍在用的图**）

`security definer`，但内部强制 `(storage.foldername(name))[1] = auth.uid()`，用户只能看到自己目录下的孤儿；仅授予 `authenticated` 执行权限。**函数只列不清，删除必须由用户勾选确认后由客户端执行。**

### 2.8 IV.1 的幂等字段清理

对 `mistake_images` / `attachments` / `ocr_jobs` 中名为 `base64`、`data_url`、`image_data`、`blob_data`、`raw_bytes`、`bytea` 之类的历史列做条件式 `drop column`（先查 `information_schema` 再删），**重复执行不会报错，也不会误删业务列**。

## 三、迁移 SQL 是否幂等 / 会不会丢数据

| 保证 | 做法 |
| --- | --- |
| 可重复执行 | 全部 `add column if not exists`、`create table if not exists`、`create index if not exists`、`on conflict do update`；约束在 `do $$ ... if not exists (pg_constraint) ... end $$` 里创建 |
| 不丢数据 | **没有任何 `delete` / `truncate` / 改列类型 / 重建表**；唯一的结构性变化是 `mistake_id` 放宽为可空（只放宽不放紧） |
| 老数据兼容 | 已有图片 `image_role` 默认 `'inline'`，`mistake_id` 非空，全部满足新约束 |
| 新库一次建好 | PART I + II + III + IV 整份粘贴执行一次即可 |
| 升级老库 | 同样整份执行一次；`supabase/selfcheck.sql` 与本文末自检 SQL 验证 |

### 自检（Supabase SQL Editor）

```sql
-- 1) 图片二进制 / Base64 字段必须为 0 行
select column_name, data_type from information_schema.columns
where table_schema='public' and table_name in ('mistake_images','attachments','ocr_jobs')
  and (column_name ilike '%base64%' or column_name ilike '%blob%' or data_type = 'bytea');

-- 2) 新字段必须 9 行
select column_name from information_schema.columns
where table_schema='public' and table_name='mistake_images'
  and column_name in ('image_role','parent_image_id','crop_rect','original_size_bytes',
    'compressed_size_bytes','is_original_backed_up','original_backup_note','draft_id','public_url');

-- 3) 桶必须私有
select id, public, file_size_limit from storage.buckets where id='mistake-images';  -- public=false, 8388608

-- 4) 新表 RLS
select tablename, rowsecurity from pg_tables
where schemaname='public' and tablename in ('deleted_images','image_purge_failures');  -- 2 行 true

-- 5) 孤儿清单（应能列出刚上传但放弃保存的临时图）
select * from public.list_orphan_images_v4(10);
```

## 四、新架构一图看懂

```
手机拍照 / 相册 / 拖拽 / 粘贴
        │
        ▼  ① 浏览器压缩（最长边 1600、质量 0.8、WebP、目标 200–500KB）
        │      同时用 canvas 生成 thumbnail（不依赖付费图片变换）
        ▼  ② POST /api/images/upload（服务端校验登录/类型/≤8MB/数量/归属）
        │      路径 <uid>/mistakes/<整题|inline|cropped|thumbnail>/<实体id>/<uuid>.webp
        ▼  ③ 上传成功后才写 mistake_images（只写 storage_path + 元数据）
        │      image_role=original|cropped|inline|thumbnail
        ▼  ④ 返回签名 URL → 预览 / 列表 / 详情 / 打印 / 分享 / AI OCR 全部走 Storage URL
                          │
                          └── 原图离线副本：用户手动「导出原图包」zip（可选，网页不依赖）
```

- **数据库**：只有路径与元数据，零二进制 / 零 Base64 / 零 Blob。
- **Storage**：私有桶 + RLS，用户只能访问自己目录下的文件。
- **本地电脑**：只存用户主动下载的离线副本；关机、换电脑、重装系统都不影响网页取图。

## 五、Storage 配置一览（写进手册）

| 配置项 | 值 | 说明 |
| --- | --- | --- |
| bucket 名称 | `mistake-images` | 沿用现有，不新建桶、不改环境变量 |
| 是否公开 | **否（私有）** | 通过 signed URL 访问；若改用公开桶，风险与替代见 `docs/05` |
| 单文件上限 | 8 MB（bucket `file_size_limit`） | 前端压缩后一般 200–500KB，留足余量 |
| 允许 MIME | jpeg / png / webp / gif / heic / heif | bucket 白名单 + 服务端路由二次校验 |
| signed URL 有效期 | 3600 秒（1 小时） | 展示时现签、不落库；**分享页按分享链接剩余时间取较小值** |
| 路径规则 | `<uid>/mistakes/<用途>/<实体id>/<uuid>.<ext>` | 首段必须是自己的 uid，Storage RLS 强校验 |
| service_role key | **仅服务端环境变量，绝不进前端 / 日志 / README** | 分享页用 `createAdminClient()` 白名单读取 |
